# 项目说明文档

## 1. 项目目标

该项目是一个“超大规模本地文件迁移服务”，目标是在服务化形态下完成海量文件从一个目录树到另一个目录树的可靠迁移。与一次性脚本不同，它强调：

- 可恢复
- 可观测
- 可调度
- 可控制
- 可扩展

## 2. 系统分层

项目按典型后端服务拆分为以下层次：

- `controller`：对外暴露 REST API
- `service`：承载规划、执行、调度、监控等核心业务逻辑
- `repository`：数据访问层
- `domain`：实体和枚举
- `dto`：接口请求与响应模型
- `config`：线程池、属性、过滤器、健康检查等基础设施

## 3. 核心流程

### 3.1 规划阶段

规划入口是 [ScalableTransferPlannerService.java](/C:/Users/小楠同学/Documents/demo/src/main/java/com/example/filetransfer/service/ScalableTransferPlannerService.java:1)。

处理链路：

1. 校验源路径和目标路径
2. 创建 `TransferTask`，状态设置为 `PLANNING`
3. 初始化聚合进度
4. 后台扫描源目录
5. 将扫描结果切分成批次
6. 持久化批次及文件记录
7. 更新任务为 `PLANNED`

### 3.2 执行阶段

执行入口是 [ScalableTransferExecutionService.java](/C:/Users/小楠同学/Documents/demo/src/main/java/com/example/filetransfer/service/ScalableTransferExecutionService.java:1)，真正的执行主体是 [ScalableTransferExecutionWorker.java](/C:/Users/小楠同学/Documents/demo/src/main/java/com/example/filetransfer/service/ScalableTransferExecutionWorker.java:1)。

执行链路：

1. 校验任务状态是否可执行
2. 获取任务级锁，避免重复执行
3. 重建调度热队列
4. 根据调度策略拉取批次
5. 依据背压判断决定是否派发
6. 执行批次内文件复制
7. 刷新文件状态、批次状态、任务进度
8. 完成后更新任务状态

## 4. 调度策略

当前策略名：

```text
temperature-priority-backpressure
```

策略特征：

- 按 `HOT / WARM / COLD` 对批次分层
- 每个批次有 `schedulingPriority`
- 支持 `hot/warm/cold` 不同派发节奏
- 支持线程池、队列、在途字节数、冷批次并发等背压判定

目标是：

- 让小而快的批次更早完成
- 避免超大批次长期独占资源
- 在资源紧张时主动减速

## 5. 断点续传设计

文件复制由 [ScalableFileCopyService.java](/C:/Users/小楠同学/Documents/demo/src/main/java/com/example/filetransfer/service/ScalableFileCopyService.java:1) 负责。

关键机制：

- 目标文件先写入 `.part`
- 复制进度会落到数据库
- 恢复时优先以 `.part` 实际长度为准
- 复制完成后进行校验并 promote 到正式文件

这样做避免了“数据库进度比临时文件更大时写出空洞文件”的风险。

## 6. 状态持久化

核心表包括：

- `transfer_tasks`
- `transfer_batches`
- `scalable_file_records`
- `transfer_progress`

设计原则：

- 任务层保存全局状态
- 批次层保存调度与执行单元状态
- 文件层保存细粒度恢复点
- 聚合进度单独存储，便于快速查询摘要

## 7. 热状态与运行态

运行时状态分两类：

- 冷状态：数据库中的任务、批次、文件、进度
- 热状态：在途文件数、在途字节数、调度背压计数、控制信号

当前实现支持：

- 默认使用内存存储热状态
- 可选启用 Redis 以支持多实例共享热状态

## 9. 关键工程规范

当前代码里已经补齐了几项更贴近生产团队的约束：

- 配置属性支持启动期校验
- 分页 size 有上限保护
- 异步规划接口语义与状态机一致
- 文件状态缓冲失败会回队，不丢状态
- 文件续传不会盲信数据库偏移

## 10. 当前边界与后续建议

如果继续往“大厂正式生产”推进，优先级通常是：

1. 鉴权与审计：对执行、暂停、取消等操作补权限控制
2. 数据库治理：引入 Flyway/Liquibase，替换 `ddl-auto=update`
3. 正式数据库：从 H2 切到 PostgreSQL 或 MySQL
4. 压测与容量评估：验证百万级、千万级文件规模下的行为
5. 告警体系：基于失败率、积压、耗时、背压次数建立告警
